## ADDED Requirements

### Requirement: Every scaffolded package carries a base README

The scaffold CLI SHALL generate a base `README.md` for each package it creates,
seeded from the manifest entry, so that no scaffolded package lands without a
readme. Regenerating a package SHALL produce the readme idempotently alongside its
other files.

#### Scenario: Scaffolding a package writes a readme

- **WHEN** the scaffold runs `package <key>` for a manifest entry
- **THEN** the generated file set includes `<relpath>/README.md`
- **AND** the readme names the package and carries the conventional section
  headings ready to fill in

#### Scenario: The readme is part of the full package scaffold

- **WHEN** the scaffold runs `all` across every manifest entry
- **THEN** each package directory contains a `README.md`

### Requirement: Each package owns a self-contained test configuration

Each package SHALL own its own `vitest.config.ts`, generated by the scaffold from
the manifest, complete enough to run that package's tests on its own. No root-level
shared vitest configuration SHALL be required for a package's tests to resolve and
run.

#### Scenario: A package has its own vitest config

- **WHEN** the scaffold generates a package
- **THEN** the package directory contains a `vitest.config.ts` scoped to that
  package

#### Scenario: No shared root config is required

- **WHEN** a package's tests run
- **THEN** resolution and configuration come from that package's own
  `vitest.config.ts`, not from a root `vitest.shared.ts` or `vitest.workspace.ts`

### Requirement: The offline test suite resolves modules to source

The offline test suite SHALL resolve intra-package (`~/*`) specifiers to source
through tsconfig path mappings, and cross-package (`@indra/runtime-*`, including the
`@indra/runtime-core/inference-live` subpath) specifiers to source through a
generated alias map in each package's config, with no build step required before
tests run.

#### Scenario: A cross-package import resolves to source

- **WHEN** a test imports a symbol from another `@indra/runtime-*` package
- **THEN** the import resolves to that package's `src` without a prior build

#### Scenario: A transitive source import resolves to source

- **WHEN** a test loads one package's source, which in turn imports a second
  `@indra/runtime-*` package
- **THEN** the transitive import also resolves to source

#### Scenario: An intra-package import resolves through tsconfig paths

- **WHEN** source or test code imports through `~/`
- **THEN** it resolves to that package's own `src` via tsconfig path mappings

### Requirement: Turbo orchestrates the suite and gates type-checking first

Running tests from the root SHALL be orchestrated by turbo, caching per package so
that only changed packages rerun. Type-checking SHALL complete before a package's
tests run, in every scope, and the test runner SHALL NOT perform type-checking.

#### Scenario: Only changed packages rerun

- **WHEN** `turbo run test` runs after a change to one package
- **THEN** unchanged packages' tests are served from cache and do not rerun

#### Scenario: Type-checking gates tests

- **WHEN** a package's tests are about to run under turbo
- **THEN** that package's own type-check and its dependencies' type-checks have
  completed first

### Requirement: The type build is unaffected by test-time resolution

Test-time module resolution SHALL NOT alter how `tsc -b` resolves cross-package
types; the composite type build SHALL keep resolving them through project
references to built declarations.

#### Scenario: tsc -b stays green and uses project references

- **WHEN** `tsc -b` runs from the repo root
- **THEN** the build succeeds
- **AND** each package's source resolves its cross-package types through project
  references to the dependency's emitted declarations, not through any test-time
  alias map
