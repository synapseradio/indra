## Context

INDRA is a prompt protocol whose runtime is currently an act of inhabitation: an LLM reads `core/indra-protocol` and role-plays a deterministic interpreter of `.in` files. The protocol explicitly frames the model as "a virtual machine… deterministic execution, not creative interpretation," yet the same model also performs all inference. This conflates two responsibilities the project's philosophy wants separate. The README's own metaphor — a prism that *reveals* structure rather than inventing it — only holds if the prism (the deterministic apparatus) is actually rigid.

This design extracts the deterministic apparatus into real code so the model is left with only the generative `<...>` channel. It was derived from a five-way exploration: two passes mapping INDRA's deterministic and generative surfaces, and three mapping those surfaces onto XState v5, Effect, and BAML respectively. The three target mappings converged independently on the same shape — a single conductor runtime owning the shared world, with inference as the only non-deterministic leaf — which is the primary evidence the cut is real.

## Goals / Non-Goals

**Goals:**
- Move every deterministic mechanism (control flow, state, IO, validation, parsing) out of the model and into a runtime that behaves identically every run.
- Preserve INDRA's observable semantics: the five channels, the turn-based execution model, the staged-vs-immediate `set:` rule, the delegation call stack, and the protected namespaces.
- Support **parallel actors** over a shared transactional `&context`.
- Reduce the LLM's role to typed, bounded inference calls (one per `<...>`).
- Deliver a walking skeleton first: one command, end to end, through all three layers.

**Non-Goals:**
- Full parity with the prompt interpreter in the first change. The skeleton proves the architecture; breadth follows.
- Re-authoring the `.in` library. Existing `lib/prism/` and `commands/` files are the runtime's input.
- Changing the protocol's surface language. Where the spec is ambiguous we resolve it (seam log), but we do not redesign the syntax.

## Prior art and the central bet

The hybrid is novel as an *assembly*, not as exotic parts. Every pillar has mature prior art — deterministic state machines owning control flow (StateFlow, Google ADK, Microsoft Conductor, LangGraph, Stately/XState), typed-inference-leaf DSLs (BAML, SGLang, Outlines, Guidance, LMQL, DSPy), and BEAM-actor LLM agents (Jido, the Elixir community). What appears unpublished is *these four together*, and the genuinely thin axis is **shared transactional context**.

The nearest whole-system neighbor is **Turn — "A Language for Agentic Computation"** (arXiv 2603.08755, repo `github.com/ekizito96/Turn`; verified against the PDF, abstract page, and repo README). Turn is a compiled, actor-based language with a Rust bytecode VM. It independently arrived at three of our four pillars: the VM owns control flow, the LLM is a typed `infer T { prompt }` primitive the VM schema-validates before binding, and the process model is "derived from Erlang" — each agent has an isolated context window, persistent memory, and a mailbox. It is a credible solo/company preprint, not peer-reviewed.

Turn made the *opposite* choice on our one novel axis, and gave a reason:

> "each process maintains its own context window… This prevents context contamination between agents, a common failure mode in framework-based multi-agent systems where a shared message list accumulates context from all agents indiscriminately." (Turn §6.3)

Their argument is grounded in LLM recall ("Lost in the Middle": middle-of-context recall drops to ~50%). Read precisely, **the critique is against sharing the *prompt-visible context window*, not against sharing *orchestration state*.** This is the seam that decides whether Turn's objection bites us: our `&context` whiteboard is the coordination substrate; if we do **not** dump the whole shared store into every actor's prompt — actors get scoped, typed inputs via BAML — Turn's central objection (context-window contamination) does not obviously apply. The distinction between prompt-visible context and coordination state is the thing to hold onto. Framed this way, `&context` is **a modern blackboard (Hearsay-II) with STM commit semantics**, sharing coordination state, not prompt attention.

## Decisions

### D1 — Three-layer ownership
XState owns choreography, Effect owns substrate, BAML owns inference. The boundaries are non-overlapping:

| INDRA mechanism | Owner | Becomes |
|---|---|---|
| turn loop, actors, `say`/`await`/`return` | XState | conductor + child actors; `await`→`invoke`+`onDone`, `return`→final-state `output`, `say`→idle + `PASS_CONTROL` |
| `when:`/`otherwise:` | XState | guards on ordered transitions |
| signals / `*commands` | XState | events on the conductor, handled at turn boundary |
| import resolution, schema validation, MCP tools | Effect | FS service, recursive `Effect`, `Schema.decodeUnknown`, `Layer`s |
| `&context`, `&user`, `&signals`, error taxonomy | Effect | STM `TRef`s, read-only interfaces, `Data.TaggedError` union |
| every `<...>` inference point | BAML | one typed `function` |
| personas (`identity`/`rules`/`understands`) | BAML | `template_string` emitting `{{ _.role("system") }}` |

**Invariant:** the world lives exclusively in Effect. XState context holds only control-flow/phase data. Two sources of state truth would drift; this boundary is a stated rule, not a convention.

### D2 — Concurrency is BEAM-shaped, state is STM
Each actor is internally sequential: a turn is one message handled to completion. Many actors run in parallel. Signals are delivered to a mailbox and observed at turn boundaries, never as mid-turn preemption — the same discipline BEAM uses for exit/monitor signals at receive points. This is what makes turn-boundary signal handling compatible with parallelism.

Pure BEAM is share-nothing; INDRA has a shared `&context` whiteboard (`docs/protocol/04`). We supply that one missing piece with **Effect STM**: actors share a transactional world, and conflicting commits to the same `&context` path serialize with automatic retry.

**Why STM and not a simpler staged-`Ref`.** On single-threaded Node, "parallel actors" would be a misnomer: Effect fibers are *cooperatively* scheduled — "within a single thread, only one fiber can execute at a single point in time" (Effect docs) — so two fibers can only conflict on a `TRef` across a yield point (one parked at an `await:` LLM call while another commits). At that narrow contention surface a plain staged-`Ref` plus a synchronous commit critical section would suffice, and STM would be overhead at the low-parallelism regime where it is weakest (Cascaval et al., CACM 2008).

**This is resolved in STM's favor: a genuinely parallel runtime is on the roadmap.** Single-threaded execution was a tooling limitation, not a design preference. Under `worker_threads` / multiple processes / a distributed runtime, commits become genuinely simultaneous and STM's serialize-and-retry is exactly the mechanism that prevents lost updates without hand-rolled locking. STM is therefore deliberate forward investment, and the staged-commit semantic (D3) must be built to be correct under real concurrency from the start — which makes the "LLM call must stay outside the transaction" rule (D3) load-bearing rather than theoretical.

### D3 — Staged-vs-immediate needs an overlay *on top of* STM
STM alone does not produce the staging semantic, because a `perform`-level `set:` must be invisible *even to the acting actor* during its own turn, whereas STM transaction-local writes are visible to later reads in the same transaction. Therefore:

```
per turn:  open STM transaction
           ├─ reads          → consistent snapshot of committed &context
           ├─ sequence-set   → transaction-local write (immediate, this turn)
           ├─ perform-set    → staging overlay, NOT in the tx read-view
           └─ turn boundary  → fold overlay into the tx, commit atomically
                               conflict on a shared path → STM retries the commit
```

The conductor owns the commit step, so "visible next turn" is literally true: the commit happens between turn N settling and turn N+1 dispatching. (XState v5 guards read pre-assign context, so a staged write cannot leak into a same-turn `when:` guard even by accident — the framework's evaluation order enforces the rule for free.)

**The transaction boundary must exclude the LLM call.** Effect STM forbids arbitrary effects inside a transaction by type (`STM<A,E,R>` is distinct from `Effect`), precisely because a transaction can retry, and a retried LLM call would re-fire — billing N times, producing N different completions. Our turn anatomy keeps the inference *outside* the transaction by construction: `method:`/`goal:`/`then:` (the LLM work) complete and produce plain values first; only the staged writes are folded and committed at the turn boundary. The transaction is the commit, never the inference. This is the same discipline Haskell/Effect force — compute effects outside, commit pure writes inside — and it is verified-correct against the documented design. The one implementation-level caveat to honor: a `sequence`-scoped *immediate* `set:` must not be implemented as a `TRef` write that sits in the same transaction as a later LLM-triggering effect. Immediate sequence writes are their own committed step, not part of a transaction that spans an `await:`.

### D4 — The result-capture contract becomes BAML's typed return
The protocol's SOP_02 wraps every `<...>` excursion as `{result, next_state_assertion}` parsed from free text. In the runtime this contract is replaced by a BAML function's typed return value; the "resume interpreter role" assertion is unnecessary because the runtime never left its role. Output shapes map directly: boolean gates → `bool`, ratings → `enum`, structured answers → `class`, lists → `T[]`. BAML's `{{ ctx.output_format }}` replaces every hand-written "respond with 'true' or 'false'" instruction.

### D5 — Personas are data, not actors
A persona has no `perform:` block, so it never drives a turn. It is a `{ identity, rules, understands }` record rendered into a reusable system-role `template_string` (static personas) or passed as a `class Persona` input (runtime-selected personas). "Adopting" a persona via `as:` selects which record the inference call reads; no actor lifecycle is involved.

### D6 — Walking skeleton is the first deliverable
The thinnest vertical that still exercises all three layers: one command receives user input, runs one real BAML inference, stages one `set:`, commits at the turn boundary, and produces output via a terminating action. It validates the seams (especially D3 and D4) against reality before any breadth. Scoped in `tasks.md`.

### D7 — The LLM steers routing through typed data
The runtime owns control flow; "barred from routing" is too absolute. INDRA already works this way: the LLM writes a typed value into context (`&context.tree.mode: ${<deepen or broaden>}`) and a deterministic `when:` guard routes on it (`lib/prism/modules/tree_of_thought.in`). The model influences direction only through data; the runtime decides transitions.

INDRA's actual dispatch is closed and static: every `component_ref` is a literal `@id` (`core/indra-protocol:807-808`); there is no computed-name syntax (`${...}` interpolates values, never component names); and `become:` — the one parameterized-instantiation construct — is unused across `lib/prism/` and `commands/`. So parity needs only static dispatch, and there is no existing dynamic-dispatch capability to preserve.

The data may also *name* a target the runtime then instantiates. That is a deliberate extension, not a preservation requirement, and its mechanism belongs to D10: static `await:`, parameterized `become:`, and open instantiation collapse into one `spawn`.

### D8 — Typed inference leads with a reasoning field
A bare typed output risks the format-restriction reasoning degradation Tam et al. (EMNLP 2024) measured. Mitigation: every inference `class` declares a free-form `reasoning` string field first, emitted before the typed fields, so the model produces chain-of-thought tokens before committing the typed value. `{{ ctx.output_format }}` plus declaration-order emission makes this native in BAML. The degradation largely disappears with this field (dottxt reproduction); residual model-dependence (Castillo) is measured by the de-risking experiment, not assumed.

### D9 — Inference and composition are separate layers; pure-function `<...>` are not inference
"Translate every `<...>` into a typed function" is wrong twice. First, `base.in` defines pure functions (`count`, `has_content`, `get_first`) as `<...>` calls — asking an LLM to count a list. These are not inference and become host-language pure functions, never BAML calls; mechanical translation would encode a latency/cost/nondeterminism bug as a typed contract. Second, `${<...>}` — an inference spliced into a prose template, sometimes back-referencing a generation earlier in the same stream (`query_analysis.in`, `thinking_primitives.in`) — is composition, not one inference, and has no BAML primitive. Recipe: each genuine inference becomes a typed function (per-operator, absorbing independent multi-slot templates into one class); splicing and back-referencing live in a composition layer above the functions. Risk: if that layer degrades to hand-written host code, INDRA stops being a language; keeping composition expressible in the protocol is the boundary that keeps it one.

### D10 — INDRA actors are interpreted by one generic registered actor, parameterized by AST data
XState v5 `spawn(logicValue, { input, systemId })` accepts inline actor logic built at runtime (verified, stately.ai/docs/spawn), so an actor can be created mid-run from data. The one hard limit is persistence: inline runtime-built logic cannot auto-rehydrate, because restore resolves children by a `src` string and the builder function does not re-run (stately.ai/docs/persistence; xstate#4226, #4171).

Resolution, which removes the limit and unifies dispatch: do not compile each INDRA actor to a distinct XState machine. Register ONE generic "INDRA-actor interpreter" in `setup({actors})`, and treat each INDRA actor definition — its identity/rules/understands/perform AST — as serializable `input`. Then static `await: @name`, parameterized `become: @persona`, and any future open target are the same operation: `spawn('indraActor', { input: blueprint, systemId: name })`. The variation is data and the logic is a fixed registered `src`, so durable execution and rehydration work. This is also the natural shape: an INDRA actor is a generic interpreter parameterized by its definition, and the statechart structure lives in the parsed program rather than in N hand-authored machines.

Tradeoff: less of XState's per-actor static typing and per-actor visualization, since all INDRA actors share one generic logic. The conductor and the fixed turn-loop skeleton remain real statecharts; only the per-INDRA-actor behavior is data-parameterized.

### D11 — Bootloader end state is a split, and its rewrite is the last seam
`core/indra-protocol` currently serves two roles at once: it is the semantic authority for INDRA and the activation prompt for the legacy LLM-inhabited runtime. The end state splits them. The semantics migrate to `openspec/specs/` as the single source of truth — the capability deltas in this change are that migration's first installment — and `core/indra-protocol` later shrinks to a thin legacy activation shim that points at the specs rather than restating them. The rewrite of the bootloader itself is deliberately the **last** seam, ordered after spec capture, the expression evaluator, and the parser, because each of those produces the verified material the shim will reference. Until then the bootloader stays as-is: it remains evidence of intent (per the seam-log stance), and rewriting it before the specs are settled would just create a second drifting copy.

## Seam log — curation decisions across disharmonious sources

The source set (`core/indra-protocol`, `docs/protocol/01–04`, the `.in` library) is expected to disagree with itself. It accreted as prose the LLM inhabits, and it outsources judgment to the model in places that look deterministic. This log is the curation record: for each seam it keeps the good reading, repairs the weak one, or specifies semantics no source supplies. The governing stance is **repair semantics freely, preserve syntax, drop dead parts with a note** — the syntax is the one thing the port does not redesign (Non-Goals). "The protocol says X" is evidence here, never authority.

Each entry records the **Decision** and the spec capability it **drives**. Status: S1–S11 **resolved**; entries from S12 on carry their status inline.

- **S1 Result capture (SOP_02).** *Decision:* typed BAML return (D4). Discard `next_state_assertion` entirely — it is an artifact of the LLM-inhabits-VM model, re-asserting a role the runtime never leaves. Malformed output is handled by BAML's parser plus retries; on retry exhaustion the turn fails with a tagged `InferenceParseError` *before* the boundary commit, so nothing staged is folded. *Drives:* inference-layer.
- **S2 Two non-isomorphic turn definitions.** `docs/protocol/03` commits staged writes at step 8 of the *current* turn; SOP_06 applies them at step 2 (`UPDATE_CONTEXT`) of the *next* turn and adds loop suspend/resume steps doc 03 omits. *Decision:* one canonical conductor-owned cycle. The two are the same commit viewed from opposite sides; model it as a single boundary step between turn N settling and N+1 dispatching (D3), so "visible next turn" is literally true. Canonical cycle: identify active actor → `method:` → `goal:` → `then:` (guards read committed state) → loop-suspension check (kept from SOP_06) → terminator → boundary commit. SOP_06's bare `INITIALIZE_CONTEXT`/`END_TURN` bookkeeping is dropped; the runtime owns it implicitly. *Drives:* interpreter-runtime.
- **S3 Sequence-vs-staged precedence.** No source addresses the collision where one turn both sequence-sets and perform-stages the same `&context` path. *Decision:* the staged perform-set wins at commit. The commit is the actor's considered end-of-turn intent; the sequence write was intermediate computation. *Drives:* context-state (the missing same-path scenario).
- **S4 `instruction`-as-data execution (SOP_05).** SOP_05 says "execute" the `instruction` payload but never bounds it; the protocol's own example (line 577) is a `read_file:` directive — a parseable INDRA action, not free prose. *Decision:* an `instruction` MUST parse as a restricted `executable_unit` subset — `read_file_directive`, `set_block`, `emit_action`, `log_action` — with no terminators and no host-language eval. A parse failure or a disallowed construct raises the protocol's own `instruction_failed` signal and resumes. This repairs "execute a string" into a bounded sublanguage. *Drives:* signal-system.
- **S5 `use_clause` scoping conflict.** The SOPs say `use` is attention-only (full file always inlined); the linter section says only named components are imported. *Decision:* keep both good halves — inline the full file physically (SOP_01 is right; transitive imports must resolve), but when a `use_clause` is present, bind and expose only its listed symbols (the linter's explicit surface is the better engineering). Absent a `use_clause`, all top-level components are visible. *Drives:* module-resolution.
- **S6 Expression evaluator.** The surface grammar exists (`is`/`greater_than`/`exists()`/ternary/`${...}`, lines 839–854); no source gives it semantics. *Decision:* specify a total, side-effect-free evaluator. `is` is type-strict structural deep-equality (no coercion; different types compare false); `not` is its negation. Ordered comparators are defined only when both operands are numeric, else `ExpressionTypeError`. Truthiness: `false`, `null`, `0`, `""`, `[]`, `{}` are falsy, everything else truthy. `exists(&p)` is true iff the path resolves to a present, non-null cell. Ternary is standard; `${expr}` evaluates then stringifies. *Drives:* interpreter-runtime (candidate for its own `expression-evaluator` sub-capability).
- **S7 `become:` vs personas.** Not actually a contradiction once the grammar is read: `become_action` (line 879) is `become ':' component_ref 'with' ':' object 'perform' ':' perform_block` — the inline `perform:` is part of `become`. *Decision:* the named persona supplies behavioral constraints (`identity`/`rules`/`understands`) as data; the become-site `perform:` supplies the turn logic; together they parameterize one registered interpreter actor (D10). "Personas have no `perform:`" dissolves — the `perform:` comes from the become site. *Drives:* interpreter-runtime, inference-layer (persona-as-data).
- **S8 Import dedup/cycle (SOP_01).** Static imports are silent on cycles and diamonds; dynamic imports (SOP_04) already dedup per session. *Decision:* apply the dynamic side's discipline to the static side, which simply forgot to state it. Static resolution tracks a visited-set keyed by canonical absolute path: a diamond inlines once and later refs are no-ops; a true cycle (A→B→A) halts with a fatal `ImportCycleError` naming the cycle. *Drives:* module-resolution.
- **S9 Loop continuation (SOP_07).** The protocol already specifies the preserved state (`iteration_count`, `condition`, `max_iterations`, `loop_position`, `local_state`) and its location; the only gap is that `loop_position` lives "in LLM memory." *Decision:* reify the `until:` loop as an explicit frame — a program counter into the loop-body AST plus the named fields — serialized to `&context._loop.<actor_id>.<loop_instance_id>`. SOP_07 suspend/resume becomes save/restore of this frame at the conductor. Honors the protocol's own contract; makes the counter real. *Drives:* interpreter-runtime.
- **S10 Trace gating.** `grammar_violation` output is marked "trace mode only" (line 546); `tool_failure` is non-fatal null-and-continue (line 551). *Decision:* separate visibility from control. A `grammar_violation` always halts and is always recorded in the error channel; the trace flag only gates whether its message prints. This repairs the dangerous reading where turning trace off would suppress a halt. `tool_failure` stays non-fatal. *Drives:* interpreter-runtime (halt semantics), signal-system (trace toggle).
- **S11 `*help` predicate.** The protocol (lines 609–613) routes on whether the active actor "produced help output" — an LLM judgment. *Decision:* replace it with a deterministic convention. An actor opts into help by declaring a help handler — a `when:` branch keyed on the help signal that calls `output:`. The runtime checks whether that declared handler ran and emitted output; if the actor declares none, the runtime emits the global help message (standard signals plus the `commands/` listing). No judgment remains. *Drives:* signal-system.
- **S12 Self-test violates its own grammar.** *Status: resolved.* The bootloader's mandatory self-test program defines `@test_runner` with a `perform:` block of `method:`/`goal:`/`then:` and no `output_block` (`core/indra-protocol:249-257`), but the grammar requires `perform_block ::= perform ':' INDENT output_block (…)+ DEDENT` — a mandatory leading `output_block` (`core/indra-protocol:928`). The protocol's own canonical example cannot parse under the protocol's own grammar. *Decision:* the corpus is the better evidence of intent — perform blocks throughout `lib/prism/` and the self-test treat `output_block` as optional. The grammar is repaired: `output_block` is not required in `perform:`. The runtime AST already encodes this (no mandatory output member on `ActorDef`). *Drives:* interpreter-runtime (no spec text requires a leading output block); the grammar repair lands with the parser seam.
- **S13 `&signals` missing from the execution model's namespace list.** *Status: resolved.* `namespace_rules` defines `&signals` as a protected, interpreter-written namespace (`core/indra-protocol:690-697`), but the `detailed_execution_model` namespace list omits it entirely while listing `&context`, `&user`, `&pipeline`, `&args`, `&result` (`core/indra-protocol:961-982`). *Decision:* `namespace_rules` is correct; the omission is drift, not intent. `&signals` is protected and runtime-written — already captured in context-state (protected-namespace rejection) and signal-system (runtime-only writes). *Drives:* signal-system, context-state.
- **S14 SOP_05 is structurally broken YAML.** *Status: resolved.* The signal-handling SOP's body is mis-indented — `name:` floats at the wrong depth and `trigger:` through `instruction:` fall out of the `SOP_05_UNIFIED_SIGNAL_HANDLING:` mapping (`core/indra-protocol:127-165`). A YAML parser would not attach the procedure to the SOP; only an LLM reading it as prose recovers the intent. *Decision:* the content stands as intent — intercept, translate `*commands`, log, execute `instruction` payloads per S4, update `&signals`, resume — and is captured structurally in the signal-system spec. The breakage itself is further evidence for D11: the bootloader is inhabitation prose, not a parseable artifact, and the specs are where the semantics now live. *Drives:* signal-system.
- **S15 `&dialogue` is a skeleton artifact, not protocol.** *Status: resolved for spec capture; disposition open at the parser seam.* The runtime's `Namespace` type includes `"dialogue"` and user-input ingestion writes `&dialogue.latest_dialogue_entry` (`runtime/src/effect/turn.ts:211-222`), but no protocol source defines a `&dialogue` namespace. *Decision (user, spec-capture session):* it is a skeleton-era artifact and stays out of all specs. Whether it becomes a real namespace or is removed is an open question deferred to the parser seam, when the namespace surface is finalized.
- **S16 No-branch turns are excluded statically.** *Status: resolved; runtime change pending.* As built, a turn whose `then:` matches no branch and has no `otherwise:` falls through to an implicit `return: null` (`runtime/src/effect/turn.ts:180-183`) — a silent settle the protocol never sanctions. *Decision (user, spec-capture session):* prevent the case statically rather than define semantics for it. Program validation requires every `then:` block to be total (an `otherwise:` or exhaustive guards), so a no-branch turn cannot occur at runtime. Spec'd in interpreter-runtime; the as-built implicit return is a recorded gap until load-time totality validation lands.
- **S17 `await:` resumption and `say:` routing are spec'd but unbuilt.** *Status: resolved; runtime change pending.* The protocol's delegation model resumes the awaiting actor from the await point (`core/indra-protocol:1015-1018`), and `say: to:` names which component takes the next turn. As built, the awaiting actor finalizes immediately after storing the child's result instead of resuming (`runtime/src/xstate/indra-actor.machine.ts:162-191`), and the conductor ignores `say`'s `to:` target — every `PASS_CONTROL` re-emits as host output and returns the baton to the same entry actor (`runtime/src/xstate/conductor.machine.ts:90-100`). *Decision:* the intended semantics are captured in interpreter-runtime (resume-from-await-point; `say:` routes control, `to: @user` yields for input); both are skeleton gaps to implement, not spec weakenings.

## Risks / Trade-offs

Each decision states its own trade-off inline (D2 pays overhead for unexercised parallelism; D9 risks composition leaking into host code; D10 trades per-actor typing for one generic interpreter). The risks below belong to no single decision.

- **Effect↔XState error-channel impedance.** Effect's typed errors collapse to a rejected Promise at the XState boundary, losing the type. Mitigate by rejecting with the tagged-error instance and switching on `_tag` machine-side.
- **Library API churn.** Exact current names for Effect `ManagedRuntime`/`@effect/platform` `FileSystem`, XState v5 `setup`/final-state `output`, and BAML `template_string`/`ctx.output_format` were verified during exploration but should be pinned to specific versions before building. [?]
