## Context

The runtime executes a hand-authored AST whose own header calls it "the parser's eventual output" (`runtime/src/ast/types.ts:10-11`). It is an internal shape with no contract: the only thing that reads it is the one generic interpreter, and the only thing that writes it is `programs/skeleton.ts`. That was the right scope for the walking skeleton (D6), where a single producer and a single consumer share a TypeScript module and drift is impossible.

The roadmap breaks that closure. We have decided to target the runtime with multiple front-ends — a TypeScript eDSL first, the deferred `.in` parser second — and the moment a second producer exists, the AST stops being an implementation detail and becomes the wire between independently-authored compilers and one executor. A shared-module type is not a contract; it carries no version, validates nothing at the boundary, and encodes its invariants as prose comments rather than checks.

Promoting the AST to a stable intermediate representation also closes three validation gaps the extraction change recorded and deferred, each a place where the runtime settles or spawns on a value no producer was forced to make total:

- A `then:` block that matches no branch and carries no `otherwise:` falls through to an implicit `return: null` (S16; `runtime/src/effect/turn.ts:180-183`) — a silent settle the protocol never sanctions.
- A dangling `await:` target spawns `null`: `context.actors[target]` returns `undefined`, the spawn yields `null`, and the machine carries on (`runtime/src/xstate/indra-actor.machine.ts:138-139`).
- Inference dispatch is a hand-coded string check against the single skeleton function (`runtime/src/effect/turn.ts:92`), so an unresolved reference is discovered at call time as a `ToolInvocationError` rather than at load.

The current load-time validation already walks the whole program to trace referenced `&context` paths (`runtime/src/effect/initial-state.ts:82-115`) and halts before turn one on the first uninitialized one. That walker is the seam this change extends: the same traversal that finds uninitialized paths is where totality, actor-reference, and registry-resolution checks belong.

This is a cross-cutting change. It touches the AST contract, a new validation pass invoked by the conductor before `spawning` (`runtime/src/xstate/conductor.machine.ts:47-71`), the inference dispatch in `turn.ts`, the inference layer as the first registry supplier (`runtime/src/baml/inference.layer.ts`), and the `Namespace` union that closes `ContextPath`. The decisions below resolve how the contract is shaped, validated, versioned, and bound, and they finalize the two namespace questions parked at the parser seam (S15, S19).

## Goals / Non-Goals

**Goals:**

- Promote the AST to a versioned, JSON-serializable `Program` document — the single public artifact every front-end compiles to and the only thing the runtime executes — with the serializability invariant (no functions, no class instances) stated as a contract requirement rather than a comment.
- Add a load-time validation pass that rejects a Program before the conductor spawns: schema conformance, branch totality (S16), actor-reference resolution, namespace write-protection where statically decidable, and every inference reference resolved against a registry. Define the error taxonomy for rejection.
- Revalidate rehydrated documents against the live registries before resuming.
- Define the registry contract: registries hold only the non-deterministic, host-bound leaves — inference now, MCP tools later — referenced by string name in the IR and bound to implementations at load. Everything deterministic stays out.
- Specify the version field and the compatibility policy for persisted documents: validate-and-reject or migrate, never silently reinterpret.
- Finalize the namespace surface: resolve `&dialogue` (S15), `&result` (S19), and the declared-but-unexercised `&args` so `ContextPath` is closed over a declared namespace set.
- Define the extension policy for constructs the language has but the runtime does not yet execute (`each`, `until`, `sequence`, operators, `become`, templates).

**Non-Goals:**

- Building the TypeScript eDSL or the `.in` parser. This change defines the artifact both will emit; the producers are later changes. The eDSL is unblocked by this one, not delivered in it.
- Executing the not-yet-executable constructs. This change decides how the IR *represents* them and how validation *rejects* their use against a runtime that cannot run them, not how they run.
- Building the MCP-tool capability. The registry contract is shaped so tools slot in beside inference later; no tool registry ships here (cf. S18).
- Implementing `await:` resumption or `say:` routing (S17). Those remain the interpreter's job; this change only makes the IR able to express their targets without dangling.
- Redesigning syntax. The port preserves syntax and repairs semantics (the governing stance from the extraction seam log); the IR is the AST made into a contract, not a new shape.

## Decisions

### IR1 — The IR is the AST promoted to a contract, with `types.ts` as reference implementation paired with a runtime schema

`runtime/src/ast/types.ts` becomes the IR's normative TypeScript reference: the node forms (`ValueExpr`, `GuardExpr`, `SetStatement`, `Terminator`, `Branch`, `PerformBlock`, `ActorDef`, `Program`) are the document format. Alongside it we add a runtime schema — an Effect `Schema` — that decodes an unknown value into a `Program` at the boundary, so a document arriving from a front-end or a persisted snapshot is validated structurally before any walker touches it.

*Why a schema at all.* A TypeScript type vanishes at runtime. When the only producer shared the consumer's module, the compiler was the whole contract. With independent producers and persisted documents, the boundary needs a value-level check: a hand-built object, a deserialized snapshot, or an eDSL bug can present a shape the types promised but the value violates. The schema is that check.

*Why Effect Schema over alternatives (zod, JSON Schema, io-ts).* The runtime is already an Effect program end to end, and `effect@3.21.3` ships `Schema` in the package the runtime already depends on (`runtime/package.json:18`), so this is a first use rather than a new dependency. A `Schema.decodeUnknown` failure is an `Effect` with a typed `ParseError`, which composes directly with the existing validation Effects and the tagged-error channel (the extraction change's Effect↔XState impedance mitigation switches on `_tag`). zod would add a package and a second error idiom; raw JSON Schema would validate but not decode into branded types; io-ts is the predecessor Effect Schema supersedes. The schema also gives us the serializability invariant for free at the boundary (IR2).

*Single source of truth between the type and the schema.* The type and the schema can drift. We resolve drift by deriving the TypeScript type from the schema (`Schema.Schema.Type<typeof Program>`) so the schema is normative and the type is generated, OR — if hand-written types stay clearer as documentation — by a unit test that asserts a representative `Program` literal decodes and that the derived type is assignable to the hand-written one. The direction is settled in favor of deriving the type from the schema; the open detail is only how much of the rich JSDoc on `types.ts` survives that move (Open Questions).

### IR2 — Serializability is a contract requirement enforced at the schema boundary

The AST comment says every type is "plain, serializable data. No functions, no class instances" and explains why: an `ActorDef` is handed to XState as an actor's `input` (D10), so it must survive structured serialization and snapshot persistence (`runtime/src/ast/types.ts:5-8`). The IR makes this a requirement of the format, not a property the producer is trusted to uphold.

The `Json` type (`runtime/src/ast/types.ts:15-21`) already encodes the leaf constraint structurally — a value is a string, number, boolean, null, array, or string-keyed object, and nothing else. The schema enforces it at decode: a function, a class instance, a `Date`, a `Map`, or an `undefined` leaf fails to decode and the document is rejected. This closes the gap between "the comment says serializable" and "the runtime proves serializable before it persists anything", which matters precisely because the document becomes a snapshot the runtime must rehydrate (IR6).

*Why the JSON data model, against the alternatives.* The choice separates into two decisions: the data model (what values can exist in the tree) and the encoding (how the tree becomes bytes). The JSON data model is the commitment; JSON text is only the day-one encoding. Binary encodings of the same value space — CBOR (RFC 8949), MessagePack — remain open as later ink swaps that change no document's meaning, and CBOR's deterministic-encoding profiles cover content hashing if documents ever need signing. The genuine alternatives are richer data models: Amazon Ion (real timestamps, arbitrary-precision numbers), protobuf and its zero-copy cousins (schema-defined records with field numbers, built for cross-language RPC evolution — the tolerance posture IR6 inverts). They buy scalar types no IR construct carries; counts, guard values, names, and templates all fit JSON's leaves. Human-authoring formats (YAML, TOML) are the wrong layer, since the Program is compiled output and the human surface is the `.in` file and the eDSL. Three constraints make the JSON model the fit rather than the default: XState's persistence contract requires snapshots to be JSON-serializable — "you cannot persist functions, classes, or other non-serializable values" (<https://stately.ai/docs/persistence>) — and an `ActorDef` rides inside actor input and snapshots, so the host enforces this model regardless of what the format declares; the TypeScript eDSL's natural output is JSON-shaped objects, giving the first front-end zero impedance; and the nearest precedents for a TypeScript-ecosystem program IR — ESTree/Babel ASTs, XState machine configs themselves — landed on JSON-shaped data. What would reopen the question: a semantic need for 64-bit integers or first-class timestamps as leaves (Ion), polyglot runtimes exchanging documents over RPC (protobuf), or document sizes where binary matters (CBOR, model unchanged). One sharp edge of the model is closed at decode: JavaScript's non-finite numbers (`NaN`, `Infinity`) are numbers the model cannot express — `JSON.stringify` silently writes `null` for them — so the schema's number leaf is `Schema.Finite` (`runtime/node_modules/effect/dist/dts/Schema.d.ts:2879`), never bare `Schema.Number`, keeping the round-trip promise honest for hand-built documents.

### IR3 — One ordered load-time validation pass, invoked by the conductor before `spawning`, extending the existing walker

Validation is a single pass that runs in the conductor's `validating` state (`runtime/src/xstate/conductor.machine.ts:47-54`) before `spawning`, replacing the current `validateInitial` leaf with a broader `validateProgram` that subsumes it. The pass runs the checks in a fixed order, each a stop condition:

1. **Schema conformance** (IR1/IR2): decode the document. A structural failure rejects before any semantic check runs, so later checks may assume a well-formed `Program`.
2. **Branch totality** (S16, IR4): every `then:` block is total.
3. **Actor-reference resolution**: every `await:` (and later `become:`) target, and the Program's `entry` reference (`runtime/src/ast/types.ts:136`), names an actor present in `program.actors`, closing the dangling-spawn gap (`runtime/src/xstate/indra-actor.machine.ts:138-139`).
4. **Initial-context completeness**: the existing check (`runtime/src/effect/initial-state.ts:96-115`) — every referenced `&context` path is initialized by the root `with:` block. Kept verbatim; it already walks the tree this pass walks.
5. **Namespace write-protection where statically decidable**: a `set:` targeting a protected namespace (`&user`, `&signals`) is rejected statically rather than at commit (context-state's protected-namespace rule), because the target path is literal IR data and needs no runtime value to judge.
6. **Inference-reference resolution** (IR5): every `InferenceRef.fn` resolves against the supplied registry.

*Why one pass, not six.* The traversal is the cost; the checks are cheap visitors over the same nodes. `initial-state.ts` already demonstrates the shape — `collectFromActor` walks branches, guards, sets, and terminators once (`runtime/src/effect/initial-state.ts:70-79`). The new checks are additional visitors threaded through that same walk, not six independent traversals.

*Why this order.* Schema conformance first because every later check assumes a decoded `Program`. The semantic checks are independent of each other and could run in any order, but reporting the first failure deterministically (rather than a set) keeps the error surface small and the conductor's `onError → halted` edge unchanged. The pass fails with the first violation in this order.

*Alternative considered: validate lazily, at first use of each construct.* Rejected. The protocol's whole stance is that a turn must not settle on an unsanctioned value; discovering a dangling `await:` or an unresolved inference only when control reaches it reintroduces the call-time-failure the proposal exists to remove, and makes a program's validity depend on which branches a run happens to exercise.

### IR4 — Branch totality is structural: an `otherwise:` or an explicitly-exhaustive guard set

S16 requires every `then:` block to be total. "Total" means the block carries an `otherwise:` branch (a `Branch` with no `when:`, which the AST already models — `when` is optional, `runtime/src/ast/types.ts:105-109`) or its guards are provably exhaustive. We decide totality structurally: a block is total iff its final branch has no `when:` and every earlier branch has one — a guardless branch before the end makes the branches after it unreachable, so the check rejects that position rather than letting dead branches pass silently. General guard exhaustiveness (proving a set of `is`/`isNot`/`exists` guards covers every possible world) is undecidable in the value domain and not worth a solver here.

*Trade-off.* A program whose guards genuinely cover every case but omits the `otherwise:` is rejected and must add a redundant `otherwise:`. We accept the false-reject: an explicit `otherwise:` is cheap, reads as intent, and is the same discipline a `switch` exhaustiveness check imposes. The validation error names the actor and the block (the spec scenario, `openspec/specs/interpreter-runtime/spec.md:28-32`), so the fix is mechanical.

*Note on the as-built fall-through.* Until this lands, `turn.ts` still settles a no-branch turn as `return: null`. That implicit return is the recorded gap S16 tracks; this change is its implementation. The validation makes the runtime path unreachable rather than redefining what it does.

### IR5 — Registries hold only non-deterministic host-bound leaves; everything deterministic is IR data or a runtime builtin

The registry contract draws one line: a registry holds the leaves whose behavior is non-deterministic and host-bound, referenced from the IR by string name and bound to an implementation at load. Inference functions are the only such leaf today; MCP tools are the next. Everything deterministic stays out of registries.

This replaces the hand-coded dispatch in `turn.ts` — the `if (value.ref.fn !== "WelcomeExplorer")` check (`runtime/src/effect/turn.ts:92`) — with a registry lookup keyed by `InferenceRef.fn`. The inference layer (`runtime/src/baml/inference.layer.ts`) becomes the first registry supplier: it presents the name `WelcomeExplorer` bound to `b.WelcomeExplorer`, and validation step 6 (IR3) resolves every IR reference against that registry's key set. An unresolved reference is a load-time validation error, not a call-time `ToolInvocationError` — which is the strictly-better failure the proposal names, moving a whole class of error from "discovered mid-run on some branch" to "discovered before turn one".

*The registry's surface.* Two operations are enough: a membership check that validation step 6 calls (`has(name)`), and a binding lookup that dispatch calls (`get(name)`), where a binding takes the call's input and returns an `Effect` — the same channel the inference layer already presents. Anything richer, such as enumeration or per-binding metadata, waits for a consumer that needs it.

Three things stay deterministic and therefore out of registries, each with a home:

- **Guards and value expressions** are IR data, evaluated by the runtime's specified evaluator (S6). A `when:` is a `GuardExpr` node the interpreter reads; it is never a host predicate the registry supplies.
- **Operator definitions** are a table in the `Program` document, like the actor table — data the runtime evaluates, not behavior the host injects. (The table's exact shape is deferred to when operators are executed; IR7 governs how the IR carries it meanwhile.)
- **The D9 pure-function leaves** (`count`, `has_content`, `get_first`) are runtime builtins, versioned with the runtime, not host-swappable registry entries. D9 settled that asking an LLM to count a list encodes a bug as a contract; making them builtins keeps them deterministic and keeps the host from redefining `count`.

*Why string-name indirection rather than embedding behavior.* The IR must stay serializable (IR2) and rehydratable (D10), so it cannot carry a function. A name in the data, bound to behavior at load, is the only shape that survives persistence. It is also what lets the same document run against different hosts: a test host binds `WelcomeExplorer` to a stub (the offline-core path the inference layer already supports via `InferenceStub`, `runtime/src/baml/inference.layer.ts:19-20`), a production host binds it to the live model, and the document does not change.

*Alternative considered: one flat registry for every leaf, deterministic or not.* Rejected. Putting `count` in a host registry would let a host swap pure-function semantics per deployment, reintroducing the nondeterminism D9 removed, and would blur the one line the contract needs: host-bound and non-deterministic on one side, runtime-versioned and deterministic on the other.

### IR6 — A version field with a validate-and-reject compatibility policy; rehydration revalidates against live registries

The root `Program` document carries a version field. The field is a string, and "recognize" is exact membership in the runtime's declared set of supported versions — no range, prefix, or structural interpretation. The compatibility policy for a persisted document is validate-and-reject or migrate — never silently reinterpret.

The bump trigger is fixed by the division of labor between the two gates: capability answers "does this document use something I cannot run", version answers "would I misread something I can run". Additive growth of the format — new node forms under the IR7 extension policy — never bumps the version, so a document using only existing forms stays readable by every runtime that ever supported version `"1"`. A change to the meaning of an existing form always bumps it, because that is the one hazard the capability gate cannot express: every construct in such a document is individually supported, and the runtime would not fail to run it — it would run it and mean something else. A snapshot whose version the running runtime does not recognize is rejected with a typed error at rehydration; it is not best-effort-read against the current schema, because a field that changed meaning between versions would be reinterpreted silently, which is the one outcome the policy forbids.

Rehydration also revalidates against the live registries and the loaded runtime's capability set (IR7), not only the schema. A snapshot persisted when the host bound a set of inference functions may be resumed against a host that binds a different set, and a runtime that executed a construct at persist time may have been swapped for one that does not — capability narrowing is the same drift as a dropped binding. So rehydration re-runs IR3's resolution and capability checks against the current host before the conductor resumes, and a now-unresolvable reference or now-unsupported construct rejects the resume rather than failing mid-turn after restore.

*Why reject rather than migrate, for now.* A migrator is real code that must exist before there is a second version to migrate from. Shipping validate-and-reject first means the runtime never silently mis-reads a document, and a migrator is added when a version transition with live persisted snapshots actually arrives (Open Questions). The policy statement — "validate-and-reject or migrate, never silently reinterpret" — admits the migrator without requiring it today.

*Why the opposite of protobuf's tolerance.* The most familiar system for schema evolution chose the other policy on both axes, deliberately. Protobuf parses messages carrying fields it does not recognize, preserves them, and re-emits them on serialization — proto3 briefly dropped unknown fields and walked it back in v3.5 because intermediaries that re-serialize messages were losing data (<https://protobuf.dev/programming-guides/proto3/> unknown-fields section; the restoration timeline is in the v3.4.0 release notes, <https://github.com/protocolbuffers/protobuf/releases/tag/v3.4.0>). And proto3 removed `required` outright because requiredness breaks compatibility between independently deployed binaries — the protobuf team's own framing is that "required fields are generally considered harmful and violating protobuf's compatibility semantics" (<https://stackoverflow.com/a/31814967>), and required fields were "part of the root cause of many outages in Google's early use of Protobuf" (<https://buf.build/blog/totw-8-never-use-required>). That tolerance is correct for protobuf's artifact and wrong for ours, because the artifacts differ in kind. A protobuf message is data in flight between peers that upgrade independently; the parser is frequently not the semantic consumer (a proxy routes it, a log store persists it), so partial understanding is useful and unknown data can be carried through untouched for whoever does understand it. A Program is executed, not forwarded: the runtime is the only consumer, and it must hold semantics for every node it runs. There is no downstream party to preserve unknown constructs for, and "skip what you don't recognize" applied to an executable document means running a different program than the author wrote — precisely the silent reinterpretation this policy forbids. Protobuf can afford tolerance at the wire because it pushes validation to the application layer; for an executable document the application layer *is* the runtime, so validation concentrates at load. The IR does keep protobuf's real lesson at the layer where it applies: IR7 forward-declares constructs so the format decodes documents the current executor cannot yet run — tolerance in the format, strictness at execution, with the capability check failing loudly in between.

### IR7 — The IR format defines not-yet-executable constructs; validation rejects their use against a runtime that cannot run them

The language has constructs the runtime does not yet execute: `each`, `until`, `sequence`, operators, `become`, and prose templates. The IR format defines node forms for them so a front-end can emit them and the artifact stays stable as the runtime catches up — the format is the contract for every producer, not only for what the current executor runs. But a document that *uses* a construct the loaded runtime cannot execute is rejected at load, naming the construct, rather than spawning into a half-implemented path.

Concretely: the schema (IR1) admits these node forms as the format grows to include them, and the loaded runtime advertises a capability set — the constructs it executes. Validation (IR3) checks the document against that set and rejects use of an unsupported construct with a clear error ("actor X uses `until:`, which this runtime version does not execute"). This is the extension policy: the format is forward-declared and one contract across producers, while execution is gated by what the running runtime actually implements, so neither a front-end nor a persisted document can drive the interpreter into a construct it has no semantics for.

*Why not just omit the constructs until they run.* Because then every front-end targets a moving format and a document emitted today might not parse against tomorrow's schema. Defining the forms now, and gating execution by capability, lets the eDSL and the parser commit to one artifact shape while the runtime fills in executors behind a check that fails loudly instead of silently.

### IR8 — Finalize the namespace surface: add `&result`, remove `&dialogue` and `&args`

The IR closes `ContextPath` over a declared namespace set, which forces the two questions the extraction change parked at the parser seam and a third the spec review surfaced: the declared-but-unexercised `&args`.

**`&result` is added (S19).** interpreter-runtime requires an awaited return with no `store_in:` to land in `&result`, readable by the resumed actor (`openspec/specs/interpreter-runtime/spec.md:48-51`). As built, `storeIn` is required on the `await` node (`runtime/src/ast/types.ts:93-97`) and `&result` is not a member of the `Namespace` union (`runtime/src/ast/types.ts:36`), so the fallback has nowhere to land. The IR adds `&result` to the namespace set and makes `storeIn` optional on the `await` terminator, so the `store_in`-absent case is expressible. `&result` is runtime-written and program-readable, the same protection class as `&user` and `&signals` for writes. The interpreter behavior that fills it (resume-from-await-point, S17) is not built here; this change makes the target expressible so that build has somewhere to write.

**`&dialogue` is removed (S15).** The `Namespace` union includes `"dialogue"` and user-input ingestion writes `&dialogue.latest_dialogue_entry` (`runtime/src/effect/turn.ts:211-222`), but no protocol source defines a `&dialogue` namespace; the extraction change ruled it a skeleton-era artifact kept out of all specs, with disposition deferred to namespace finalization. This is that finalization. We remove `&dialogue` from the namespace surface: the user-input ingestion that writes it is the only writer, and that path moves to a defined namespace (`&user`, which the spec already designates for user input and which user-input ingestion is the privileged writer of) or is dropped if nothing reads it. Because removal touches the live ingestion path rather than only the type, it is the one namespace decision that warrants explicit confirmation before the edit (Open Questions); the recommendation is removal.

**`&args` is removed.** The union's fifth member is declared for "the current signal/command arguments" (`runtime/src/ast/types.ts:33-36`), but the declaration is its only appearance: no runtime path reads, writes, or parses it, no test exercises it, and the signal system carries arguments inside the signal payload object — `{command: 'trace', args: ['on']}` (`openspec/specs/signal-system/spec.md:21`) — rather than through a context-path namespace. Closing the surface without it removes a declared slot, not a behavior. If signal dispatch later needs a namespace for in-flight arguments, that change reopens the question with an actual consumer in hand.

*Trade-off.* Finalizing the namespace union is a breaking change to `ContextPath`, the closed type the IR depends on, and it touches the store, `path.ts`, and the initial-state walker. The break is the point: an open namespace set cannot be a contract, and the IR's value is that `ContextPath` is closed over exactly the namespaces the runtime addresses.

## Risks / Trade-offs

- **Schema/type drift** → Resolve by deriving the TypeScript type from the Effect Schema (IR1) so the schema is the single source; a decode test over a representative `Program` literal guards the boundary. The residual cost is migrating the rich JSDoc on `types.ts` into schema annotations.
- **Totality false-rejects a guard-exhaustive block** (IR4) → Accept. Require a structural `otherwise:`; the redundant branch is cheap and reads as intent. A guard-exhaustiveness solver is out of scope and out of proportion.
- **Validate-and-reject breaks resume across a version bump** (IR6) → A persisted snapshot from an older runtime is rejected at rehydration until a migrator exists. Accept while there is one version; revisit when a real transition with live snapshots arrives.
- **Load-time registry resolution requires the host to wire every referenced function** (IR5) → A program referencing inference the host never bound now fails at load rather than at call. This is the intended improvement, but it does move the failure earlier in a way that a host with a partial registry will feel immediately; the error names the unresolved function so the fix is to bind it.
- **Namespace finalization is a breaking change** (IR8) → Closing `ContextPath` touches the store, `path.ts`, `initial-state.ts`, and the ingestion path that writes `&dialogue`. Sequence it as its own step with the namespace-surface tests leading, and confirm the `&dialogue` removal before editing the live ingestion path.
- **Effect Schema is a first use in the runtime** → Although `effect@3.21.3` already ships it (no new package), no runtime module imports `Schema` today. The API surface is pinned against the installed version: `Schema.decodeUnknown` (returns an `Effect` with the parse failure in the error channel), the `Schema.Schema.Type` extractor, and the `Struct`/`Union` combinators are all present in the shipped declarations (`node_modules/effect/dist/dts/Schema.d.ts:337`, `:155`, `:1363`, `:652`; verification table in `openspec/changes/define-program-ir/research/what.md`). One precision: the failure class is exported as `ParseResult.ParseError` from `effect/ParseResult` — `Schema` exports no `ParseError` name, so imports must use the `ParseResult` module.

## Migration Plan

The change is additive at every step until the final namespace edit, so each step lands and is tested before the next.

1. **Schema and reference type (IR1, IR2).** Add the Effect `Schema` for `Program` beside `types.ts`; derive or assert the TypeScript type against it; add a decode test that accepts a valid skeleton `Program` and rejects a non-serializable leaf. No behavior change yet.
2. **Broaden validation (IR3, IR4).** Extend the `initial-state.ts` walker into a `validateProgram` pass adding totality and actor-reference checks; define the rejection error taxonomy. Rewire the conductor's `validating` state from `validateInitial` to `validateProgram` (`runtime/src/xstate/conductor.machine.ts:47-54`). The existing initial-context check is subsumed unchanged.
3. **Registry contract and inference dispatch (IR5).** Introduce the registry abstraction with the inference layer as its first supplier; replace the hand-coded dispatch in `turn.ts` (`runtime/src/effect/turn.ts:92`) with a registry lookup; add the load-time inference-resolution check to the pass. The single-function skeleton path is the first registry entry, so the refactor is behavior-preserving for the skeleton.
4. **Versioning and rehydration revalidation (IR6).** Add the root version field; add the rehydration path that revalidates a persisted document against the schema and the live registries before resume; ship validate-and-reject (no migrator).
5. **Extension policy (IR7).** Add the runtime capability set and the validation check that rejects use of an unsupported construct, naming it. Define the not-yet-executable node forms in the schema as the format admits them.
6. **Namespace finalization (IR8).** Add `&result` and make `await` `storeIn` optional; confirm and then remove `&dialogue`, moving or dropping the ingestion write; drop `&args` from the union (a declaration with no reader or writer, so no behavior moves). Lead with the namespace-surface tests. This is the one breaking step and is sequenced last.

**Rollback.** Steps 1–5 are additive gates and a behavior-preserving refactor; reverting any one restores the prior load path without touching committed-state semantics. Step 6 is the only step that changes a public type, and it is isolated so it can be reverted independently.

## Open Questions

- **`&dialogue` final disposition (IR8, S15).** Recommendation is removal, but it edits the live user-input ingestion path (`runtime/src/effect/turn.ts:211-222`), so it needs explicit confirmation: remove entirely, or redirect the `latest_dialogue_entry` write to `&user` before dropping the namespace. Decide before step 6.
- **Schema-versus-type single source (IR1).** Derive the TypeScript type from the schema (schema normative) or keep hand-written types as documentation guarded by a parity test. Direction is "derive"; the open part is how much of the `types.ts` JSDoc moves into schema annotations versus staying as prose on the derived type.
- **When a migrator becomes necessary (IR6).** Validate-and-reject is correct while one version exists. The trigger for building a migrator — a version transition with live persisted snapshots that must survive an upgrade — is not yet on the roadmap; name it when persistence of long-lived sessions lands.
- **Operator-table shape (IR5, IR7).** Operators are deterministic and live as a table in the `Program` document, but their executor is not built here. The table's concrete schema is deferred to the change that executes operators; until then the IR carries the construct under the IR7 extension policy and validation rejects its use.
