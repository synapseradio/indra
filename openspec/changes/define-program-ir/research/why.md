# Why — design-rationale review of `define-program-ir`

## Summary

The change is unusually well-justified for its core moves. Every IR decision states a reason, and most reasons survive contact with outside precedent: the validate-everything-before-spawn pass mirrors how Wasmtime resolves and type-checks imports before it allocates or runs anything, the string-name registry indirection matches both WASM host imports and Temporal activities, and choosing Effect Schema over zod is defensible on the specific ground the design names (decode plus a typed `ParseError` in the same error channel the runtime already uses). Structural totality instead of a guard solver is the same discipline TypeScript's `never`-default and Rust's exhaustive `match` impose, and the design already cites that lineage.

The rationale the artifacts do *not* state clusters in a few places. The sharpest is a precedent the design leaves unexamined: protobuf — named in the task as a precedent for versioned-schema evolution — actually chose the *opposite* policy from IR6. Protobuf ignores unknown fields for forward compatibility; IR6 rejects an unrecognized version outright. Both are coherent, but they optimize for different worlds, and the design asserts validate-and-reject as nearly self-evident without naming the tradeoff it is making against the most familiar schema-evolution system in the field. The other open "why"s are smaller: why `&args` survives in the as-built union but is absent from the closed namespace set with no recorded disposition; why the error pass fails on first violation rather than collecting; and why `&result` joins the write-protected set rather than being merely runtime-owned.

## Questions the artifacts leave open

These name an artifact and the decision or requirement they concern. Some I can answer from outside evidence (see "What research says"); others are genuinely open and I leave them so.

**1. Why validate-and-reject, when the field's reference example for schema evolution does the opposite? (design.md IR6, lines 96–102.)** The design argues reject-don't-reinterpret from first principles — a field whose meaning changed between versions would be silently mis-read — and that argument is sound *for fields that change meaning in place*. But protobuf, the most widely deployed versioned-schema system, deliberately ignores unknown fields to get forward compatibility, and it avoids the silent-reinterpretation problem by a different mechanism: field *numbers* rather than names, and a rule never to reuse a retired tag. The design does not mention that an alternative discipline exists, nor why a Program document cannot adopt the number-stable-field approach that would let old runtimes tolerate new documents. I infer the answer is that a Program is *executed*, not merely read — an unrecognized construct is not an ignorable field but a behavior the runtime has no semantics for, so "ignore the unknown part and proceed" is unavailable in a way it is available to a data-only protobuf message. That inference is consistent with IR7, which rejects use of unsupported constructs for exactly this reason. But the design states it only for constructs (IR7), not for versions (IR6), and the version-level rationale is left implicit. Naming the protobuf contrast would strengthen IR6 rather than weaken it.

**2. Why does `&args` survive in the as-built `Namespace` union but vanish from the closed namespace set? (context-state delta spec.md:5; design.md IR8; as-built `runtime/src/ast/types.ts:36`.)** This is the unresolved surface the digest's "Loose ends" records. The as-built union is `"context" | "user" | "signals" | "dialogue" | "args"`. IR8 narrates the disposition of `&dialogue` (removed, S15) and `&result` (added, S19) at length, and closes `ContextPath` over exactly `&context`, `&user`, `&signals`, `&result`. `&args` is in the as-built union, is described in source as "the current signal/command arguments" (`runtime/src/ast/types.ts:33`), and appears in the archived protocol's own execution-model namespace list alongside `&result` (seam log S13, `core/indra-protocol:961–982`). Yet IR8 neither keeps nor drops it, and the closed set omits it without a word. I cannot resolve this from evidence — there is no recorded decision either way. Two readings are live and the artifacts distinguish neither: (a) `&args` is intentionally dropped because the signal/command-argument feature it serves is not in the walking skeleton and lands with the signal-system capability, in which case it is an undocumented removal that should get an S-style note like `&dialogue` got; or (b) it is an oversight in the closed set and `&args` should be a fifth member. The seam log treats `&signals`-missing-from-a-list (S13) as "drift, not intent" — by that same standard, `&args`-missing-from-the-closed-set deserves an explicit ruling rather than silence. **Flagging prominently: this is a contradiction between the as-built union and the closed namespace set that the change claims to finalize, and finalization with an unaddressed member is incomplete.**

**3. Why fail-on-first rather than collect-all violations? (design.md IR3, line 68; program-validation spec.md:72.)** The design gives a reason — "reporting the first failure deterministically (rather than a set) keeps the error surface small and the conductor's `onError → halted` edge unchanged." That is a real reason and it is stated, so this is not an unstated rationale. But it is worth marking that the reason is about *conductor wiring economy*, not about *author experience*, and those can diverge. A front-end compiler author (the eDSL, later the parser) debugging a freshly emitted Program would usually rather see every totality and reference error at once than fix-recompile-rediscover one at a time. The design optimizes the load path's simplicity over the producer's iteration loop. That is a legitimate call for a load-time gate whose job is to halt, and the typed-error taxonomy (program-validation spec.md:72) leaves room to batch later. I note it as a consciously-made tradeoff whose cost lands on a party (front-end authors) not yet in the room, not as a flaw.

**4. Why is `&result` write-protected, not merely runtime-owned? (design.md IR8, line 116; context-state delta spec.md:29.)** IR8 puts `&result` in "the same protection class as `&user` and `&signals` for writes." The stated reason is symmetry with the existing runtime-written namespaces. The unstated part is the threat model: `&user` is protected because a program writing user input would forge provenance, and `&signals` because a program writing the signal channel would forge control events. `&result` holds an awaited child's return value. A program that wrote `&result` directly would forge a delegation result it never awaited — which is the same provenance-forgery shape, so the protection is well-motivated. But the design does not say this; it asserts the protection class by analogy. The analogy is correct on inspection, so this is a case where the rationale is sound but compressed to a single clause; I would not call it underspecified, only terse. Confirming: the protection is justified, and the justification is forgery-of-provenance, which IR8 leaves to the reader to reconstruct.

**5. Why one schema language for the whole document rather than schema-at-the-edge plus trusted interior? (design.md IR1, lines 41–43.)** IR1 justifies *having* a schema (types vanish at runtime; independent producers and persisted snapshots need a value-level check) and justifies *which* schema (Effect Schema). It does not discuss whether the whole `Program` must be decoded or whether only the outer envelope plus untrusted leaves need it. For a document the runtime then walks node by node anyway, full-document decode and walk-time structural checks overlap. I infer the design's answer is IR3 step 1: "decode the document … so later checks may assume a well-formed `Program`" — full decode is what lets the five semantic visitors skip defensive shape checks. That is a clean separation-of-concerns argument and it is implicitly present in IR3's ordering rationale; it is simply not connected back to IR1 as "this is why we decode the whole thing, not just the boundary." The rationale exists across two decisions but is never stated as one.

## What research says

**On validate-everything-before-spawn (IR3, IR5).** Wasmtime resolves and type-checks every import and validates the module before it allocates memory, initializes state, or runs the start function. Its `InstancePre` type represents "an instance just before it is instantiated, after all type-checking and imports have been resolved," with only allocation and the start function left to do ([docs.wasmtime.dev Module API](https://docs.wasmtime.dev/api/wasmtime/struct.Module.html), [Fast Instantiation](https://docs.wasmtime.dev/examples-fast-instantiation.html)). A missing import surfaces as a link error at instantiation, not a trap mid-execution ([wasmtime#7536](https://github.com/bytecodealliance/wasmtime/issues/7536)). This is a near-exact structural precedent for IR3's ordered pass and IR5's load-time registry resolution: the unresolved-inference case the design moves "from discovered mid-run on some branch to discovered before turn one" is the same move WASM makes from "trap" to "link error." The design's claim that load-time rejection is "strictly better" than call-time failure has a mature, deployed precedent it does not cite.

**On string-name registry indirection (IR5).** Both named precedents hold. WASM modules import host functions by string module-and-name, and the host resolves those names at instantiation time; the names are a binding convention the host controls, not fixed identities ([WasmEdge host functions](https://wasmedge.org/docs/embed/c/host_function/), [secondstate.io](https://www.secondstate.io/articles/extend-webassembly/)). Temporal invokes activities through an untyped stub by name, with the worker holding an in-memory map from fully-qualified name to implementation; the calling workflow needs no registration, only the executing worker does ([Temporal Go dynamic activity](https://docs.temporal.io/develop/go/activities/dynamic-activity)). This is precisely IR5's split: the IR (like the calling workflow, like the WASM module) carries the name, and the host (like the worker, like the WASM store) carries the binding, so the same artifact runs against a stub or a live host unchanged. The design's stub-vs-live interchangeability claim (IR5, line 92) is the standard property this pattern is chosen for.

**On Effect Schema over zod (IR1).** The design's two specific grounds check out against community comparison. Effect Schema provides encode/decode for boundaries and a typed error channel; zod does validation and returns a `ZodError` in a discriminated union but without an integrated typed error channel that composes with the rest of an Effect program ([EffectPatterns schema-vs-zod](https://github.com/PaulJPhilp/EffectPatterns/blob/main/content/published/patterns/schema/getting-started/schema-vs-zod.mdx)). The interoperability between Schema and Data — parse at the boundary, then exhaustively match on tagged types — is the property IR1 leans on when it says a `ParseError` "composes directly with the existing validation Effects and the tagged-error channel" ([HN discussion](https://news.ycombinator.com/item?id=41791316)). The design's reasoning is sound; the decision is well-justified as written. The one caveat the design already marks `[?]` — that no runtime module imports `Schema` today and the API surface needs pinning — is the correct residual risk and I found nothing to retire it.

**On structural totality vs a guard solver (IR4).** The design's analogy to `switch` exhaustiveness is apt and the precedent confirms the shape of the tradeoff. TypeScript does not enforce exhaustive matching at the language level; the discipline is imposed by tooling (the `switch-exhaustiveness-check` lint rule) or by the `never`-typed default-case guard, both of which work *structurally* — they key on whether the union of literal cases is covered, not on whether arbitrary runtime guards are provably exhaustive ([typescript-eslint switch-exhaustiveness-check](https://typescript-eslint.io/rules/switch-exhaustiveness-check/), [DEV: exhaustive type checking](https://dev.to/babak/exhaustive-type-checking-with-typescript-4l3f)). Rust's compiler enforces it but, again, structurally over enum variants, not over value-domain predicates ([Medium: exhaustive matching in TS like Rust](https://medium.com/@w.xy020203/exhaustive-compile-time-matching-in-typescript-just-like-in-rust-0ba453f1f816)). IR4's "general guard exhaustiveness is undecidable in the value domain and not worth a solver" is exactly why these systems require a syntactic `default`/`otherwise:` even when a human can see the guards cover every case. The false-reject IR4 accepts is the same false-reject `never`-guards accept, and the field has judged that cost worth paying for decades. Well-justified.

**On validate-and-reject vs schema evolution (IR6) — contrary precedent.** Protobuf, named in the brief as a precedent, took the opposite policy: it *ignores* unknown fields on parse rather than rejecting, to get forward compatibility, and it prevents silent misreading not by rejecting but by using stable field *numbers* and a rule never to reuse a retired tag ([protobuf.dev best practices](https://protobuf.dev/best-practices/dos-donts/), [Understanding Protobuf Compatibility](https://yokota.blog/2021/08/26/understanding-protobuf-compatibility/)). So the design's "never silently reinterpret" goal is one protobuf shares, but protobuf reaches it through tolerant-parse-plus-stable-numbering, while IR6 reaches it through reject-on-unrecognized-version. The divergence traces to what the artifact is *for*: a protobuf message is data to be read, where ignoring an unknown field is safe; a Program is behavior to be executed, where an unknown construct has no runtime semantics and ignoring it would change execution. WASM agrees with IR6's side: it validates and rejects malformed or version-incompatible modules before running them ([Module API](https://docs.wasmtime.dev/api/wasmtime/struct.Module.html)). I infer IR6 is correct *for an executable artifact* and that protobuf's permissiveness simply does not transfer, but the design would be more defensible if it named the protobuf contrast and said why execution forecloses the tolerant-parse option — right now it argues the conclusion without acknowledging that the most familiar system in the space chose differently for principled reasons.
