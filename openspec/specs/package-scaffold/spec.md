# package-scaffold

## Purpose

The `package-scaffold` capability defines what the manifest-driven scaffold produces for each workspace package and how the offline test suite resolves and runs. Every package lands with a base README that names it and a thin `vitest.config.ts` that extends a shared `@indra/configs/vitest` base. The base config resolves intra-package `~/*` specifiers through tsconfig path mappings and cross-package `@indra/runtime-*` specifiers through a shared alias map built from the manifest, so tests run against source with no build step. Turbo orchestrates the suite, caches per package, and gates type-checking before tests, while `tsc -b` keeps resolving cross-package types through project references.

## Requirements

### Requirement: The scaffold produces a defined file set per package from the manifest

The scaffold SHALL produce, for each package it generates, a defined set of files derived from that package's manifest entry: a `package.json`, the `tsconfig` set the build uses (`src`, `test`, `aggregate`, and `build`), an `rslib.config.ts`, a `vitest.config.ts`, a `README.md`, and the `src/` and `test/` directories. Each generated file SHALL be derived from the manifest entry — its path, name, and declared dependencies — so the manifest stays the single edit point. Root-level configuration shared across packages (the root `package.json`, `turbo.json`, the base tsconfigs, and the root vitest config) is authored separately and SHALL NOT be produced by the per-package scaffold.

#### Scenario: Scaffolding a package writes the full generated set

- **WHEN** the scaffold runs `package <key>` for a manifest entry
- **THEN** the generated file set includes that package's `package.json`, its `src`/`test`/`aggregate`/`build` tsconfigs, `rslib.config.ts`, `vitest.config.ts`, and `README.md`, and ensures its `src/` and `test/` directories exist

### Requirement: The scaffold is safe to re-run over existing source

The scaffold SHALL write structure and configuration only. It SHALL NOT author or move source, and re-running it over an already-scaffolded package SHALL leave any existing `src/` and `test/` contents untouched while regenerating the package's generated configuration. Regeneration SHALL therefore be safe to run at any time without risk to hand-written source.

#### Scenario: Re-running leaves hand-written source untouched

- **WHEN** the scaffold regenerates a package that already has hand-written files under `src/` and `test/`
- **THEN** the generated configuration is rewritten and the existing `src/` and `test/` contents are left unchanged

### Requirement: Every scaffolded package carries a base README

The scaffold CLI SHALL generate a base `README.md` for each package it creates, seeded from the manifest entry, so that no scaffolded package lands without a readme. Regenerating a package SHALL produce the readme idempotently alongside its other files. The readme SHALL NOT assume the package belongs to any particular subsystem; it SHALL open with an H1 heading naming the package.

#### Scenario: Scaffolding a package writes a readme

- **WHEN** the scaffold runs `package <key>` for a manifest entry
- **THEN** the generated file set includes `<relpath>/README.md`
- **AND** the readme's first heading is an H1 carrying the package name, followed by the conventional section headings ready to fill in

#### Scenario: The readme is part of the full package scaffold

- **WHEN** the scaffold runs `all` across every manifest entry
- **THEN** each package directory contains a `README.md`

### Requirement: Each package owns a thin test config that extends a shared base

Each package SHALL own its own `vitest.config.ts`, generated by the scaffold, that extends a shared base configuration through `mergeConfig`. The base configuration SHALL live in the `@indra/configs` package and be imported as `@indra/configs/vitest`. A package's generated config SHALL add only what is particular to that package — its `test.name` and `test.root` — so the resolution and test settings that are identical workspace-wide stay in one place and the manifest stays the single edit point. No root-level orchestrator config (a `vitest.shared.ts` or `vitest.workspace.ts`) SHALL be required for a package's tests to resolve and run.

#### Scenario: A package has its own vitest config extending the base

- **WHEN** the scaffold generates a package
- **THEN** the package directory contains a `vitest.config.ts` that imports `baseConfig` from `@indra/configs/vitest` and merges in that package's `test.name` and `test.root`

#### Scenario: No root orchestrator config is required

- **WHEN** a package's tests run
- **THEN** configuration comes from that package's own `vitest.config.ts` and the shared `@indra/configs/vitest` base it extends, not from a root `vitest.shared.ts` or `vitest.workspace.ts`

### Requirement: The offline test suite resolves modules to source

The offline test suite SHALL resolve intra-package (`~/*`) specifiers to source through tsconfig path mappings, and cross-package (`@indra/runtime-*`, including the `@indra/runtime-core/inference-live` subpath) specifiers to source through a shared alias map in the `@indra/configs/vitest` base config, with no build step required before tests run. The alias map SHALL be derived from the scaffold manifest, so it is not hand-kept.

#### Scenario: A cross-package import resolves to source

- **WHEN** a test imports a symbol from another `@indra/runtime-*` package
- **THEN** the import resolves to that package's `src` without a prior build

#### Scenario: A transitive source import resolves to source

- **WHEN** a test loads one package's source, which in turn imports a second `@indra/runtime-*` package
- **THEN** the transitive import also resolves to source, because the shared alias map is process-global and rewrites the specifier wherever it appears

#### Scenario: An intra-package import resolves through tsconfig paths

- **WHEN** source or test code imports through `~/`
- **THEN** it resolves to that package's own `src` via tsconfig path mappings, scoped to that package by the config's `include`

### Requirement: Turbo orchestrates the suite and gates type-checking first

Running tests from the root SHALL be orchestrated by turbo, caching per package so that only changed packages rerun. Type-checking SHALL complete before a package's tests run, in every scope, and the test runner SHALL NOT perform type-checking.

#### Scenario: Only changed packages rerun

- **WHEN** `turbo run test` runs after a change to one package
- **THEN** unchanged packages' tests are served from cache and do not rerun

#### Scenario: Type-checking gates tests

- **WHEN** a package's tests are about to run under turbo
- **THEN** that package's own type-check and its dependencies' type-checks have completed first

### Requirement: The type build is unaffected by test-time resolution

Test-time module resolution SHALL NOT alter how `tsc -b` resolves cross-package types; the composite type build SHALL keep resolving them through project references to built declarations.

#### Scenario: tsc -b stays green and uses project references

- **WHEN** `tsc -b` runs from the repo root
- **THEN** the build succeeds
- **AND** each package's source resolves its cross-package types through project references to the dependency's emitted declarations, not through any test-time alias map
